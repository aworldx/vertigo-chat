# AGENTS.md

Правила для монорепозитория `chat`: Go + React. Phoenix сохранён как legacy.

## Обязательное

- После каждого этапа разработки запускайте быстрые целевые проверки изменённой поверхности: unit/HTTP/PostgreSQL-тесты и browser-сценарий соответствующей Go + React функции. Исправляйте найденные проблемы до следующего этапа.
- Любую проверку пользовательского интерфейса (экран, маршрут, форма или взаимодействие) основной агент выполняет через skill `verifier`; его browser-проверка обязательна и не заменяется unit-тестами, сборкой или ручным выводом HTTP.
- Основной агент не придумывает визуальное решение сам: до UI-изменения он обращается к skill `ui-designer` за макетами и критерием приёмки. Дизайнер берёт за основу текущий интерфейс и меняет только запрошенную поверхность; общие стили, навигацию и соседние экраны не переосмысливает без отдельного фундаментального предложения и явного согласия пользователя. Макеты обязательны для каждого целевого класса экранов: минимум desktop и mobile, а также tablet, landscape, popup или другие затронутые размеры. Макет — это сохранённый viewable PNG с точными viewport, route и fixture/auth state, а не текстовое описание. После Docker browser-проверки через `verifier` UI-дизайнер выполняет обязательный строгий near-pixel-perfect review только по тройке артефактов одинакового размера: исходный mock PNG, актуальный Docker browser PNG и их side-by-side плюс overlay/diff. Без любого из этих файлов, при разных данных/авторизации или при пользовательском скриншоте, противоречащем выводу, результат автоматически `REJECTED`; дизайнер возвращает конкретные замечания и не вправе назвать UI принятым.
- Полный локальный `script/check` (Go/React, контракты, покрытие, все браузерные и инфраструктурные проверки) запускайте перед push, merge или обновлением production. Он работает в закреплённой Linux-среде Docker и не требует локальных Go, Node, PostgreSQL или Elixir. По решению пользователя GitLab CI только собирает production-образы; полный quality gate выполняется локально.
- Следуйте `docs/architecture.md`: бизнес-правила — в контекстах `Chat`, `ChatWeb` остаётся тонким.
- Целевая структура, Clean Architecture/DDD, React/TypeScript и обязательные проверки зафиксированы в `docs/refactoring_target.md`. Следуйте им при рефакторинге; не считайте запланированные проверки уже внедрёнными.
- Перед продолжением миграции Go + React читайте `docs/go_react_migration_plan.md`: там рабочая ветка, ограничения, состояние и следующий шаг. Обновляйте план после каждого этапа. До нового указания пользователя не коммитьте изменения миграции, не делайте push и не меняйте production.
- Текущий UI проверяйте target browser-сценариями Go + React. Phoenix/LiveView-сравнения из `docs/migration_testing.md` и `test:browser:legacy` — только для явно запрошенной работы над legacy, не часть release gate.
- Для HTTP в Elixir используйте `Req`; не добавляйте `:httpoison`, `:tesla` или `:httpc`.
- Не затирайте чужие незакоммиченные изменения.

## React, Go и границы архитектуры

- Новый React-код и тесты пишите на строгом TypeScript. Текущий JSX — переходный долг; до расширения React-миграции переведите первый экран и подключите typecheck/lint.
- Разделяйте композицию страницы, UI-компоненты, hooks/состояние и API. Render должен быть чистым; не объединяйте запросы, URL, диалоги и отображение в одном компоненте или hook.
- Соблюдайте направление `app → pages → features → shared`; не допускайте циклов, прямых зависимостей между features и обхода их публичного API.
- В Go соблюдайте `adapters → application → domain`; domain не зависит от HTTP/БД/процессов, порты определяет потребитель, зависимости связывает composition root.
- Контексты владеют своими правилами и данными. Не обращайтесь к внутренним репозиториям другого контекста; при переносе в Go сохраняйте одного владельца записи и миграций.
- Каждый сервис обязан иметь линтеры и статический анализ. Проверяемые правила закрепляйте конфигурацией и запускайте локально и в CI; новый сервис не считается готовым без этих проверок.
- Не подавляйте ошибки массовыми исключениями, `any` или отключением strict. Точечные исключения требуют причины и задачи удаления; существующий долг не становится правилом для нового кода.

## Phoenix и LiveView

- LiveView-шаблоны начинайте с `<Layouts.app flash={@flash} ...>`; передавайте `current_scope`, если он нужен маршруту.
- Используйте HEEx (`~H`/`.heex`), `<.icon>`, `<.input>` и формы через `to_form` + `<.form for={@form}>`.
- Давайте формам, кнопкам, hook-элементам и stream-контейнерам стабильные уникальные `id`.
- Используйте `push_navigate`/`push_patch`, а не устаревшие `live_redirect`/`live_patch`; избегайте LiveComponent без необходимости.
- Для динамических коллекций применяйте LiveView streams. Контейнер обязан иметь `id` и `phx-update="stream"`; при изменении assign, влияющего на stream-элемент, вставляйте элемент в stream повторно.
- Не управляйте DOM из hook без `phx-update="ignore"`. JS храните в `apps/web/js` или colocated hooks — не в inline `<script>`.

## Elixir, Ecto и тесты

- Не применяйте `String.to_atom/1` к пользовательскому вводу. Предикаты оканчиваются на `?`.
- Не используйте `changeset[:field]` для структур; для changeset применяйте `Ecto.Changeset.get_field/2`.
- Не принимайте программно заданные поля (например, `user_id`) через `cast`; preload-ите ассоциации, используемые в шаблоне.
- Создавайте миграции через `mix ecto.gen.migration имя_в_snake_case`.
- В тестах запускайте процессы через `start_supervised!/1`; не синхронизируйтесь через `Process.sleep/1`.
- Тестируйте LiveView через `Phoenix.LiveViewTest` и селекторы с ключевыми `id`, проверяя поведение, а не сырой HTML.

## UI и CSS

- Макеты должны быть выразительными и воспроизводимыми. Перед реализацией дизайнер готовит реальные фоновые изображения/обложки, доступные шрифты, сетку и параметры адаптивности. AI-картинка служит визуальным направлением; итоговый эталон собирается из этих ресурсов с настоящими текстом и элементами управления, сохраняется до реализации и не подгоняется под неё. Не упрощайте утверждённую композицию ради прохождения сравнения. Не добавляйте придуманные генератором функции без согласования.
- Используйте Tailwind и собственные CSS-правила; не используйте daisyUI и `@apply`.
- Сохраняйте Tailwind v4 `@import "tailwindcss" source(none)` и `@source` в `apps/web/css/app.css`.
- Не подключайте vendor-скрипты или стили напрямую из layout; импортируйте их в `app.js`/`app.css`.
- Поддерживайте адаптивность, выверенные отступы, типографику, состояния hover/loading и доступность.

## Справочник чата и подсказки Кармика

- При добавлении, изменении или удалении пользовательской функции в том же изменении обновляйте `apps/web/src/shared/chatHelp.ts`: точные действия, ограничения и актуальные названия элементов UI. Этот каталог общий для `/help` и личных подсказок Кармика.
- Команды регистрируйте в `apps/web/src/shared/chatCommands.ts` с темой помощи; меню, автодополнение и `/help` используют этот единый список. Синхронизируйте обработчик `useRoomCommands.ts`.
- Для новой темы обновляйте `HelpTopic` в `contracts/openapi/chat.yaml`, генерируйте DTO и добавляйте распознавание с тестом в `apps/api/internal/karmik/domain/help.go` и `help_test.go`. Покройте естественные формулировки вопроса и ложные срабатывания.
- Проверяйте реальные сценарии инструкций и приватность: метаданные помощи передаются только в ack автора, никогда в общей истории/snapshot. Не описывайте запланированные функции как работающие.
