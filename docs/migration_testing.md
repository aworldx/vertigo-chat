# Как проверять переход на Go + React

Каждый перенесённый сценарий проверяется на совместимость поведения и внешнего
вида со старой реализацией. Цель миграции — сохранить продукт: шрифты, композицию,
отступы и взаимодействия. Видимые отличия исправляются до принятия этапа, если
пользователь отдельно не согласовал изменение дизайна.

Этот документ задаёт процедуру проверки. Для самостоятельного Go web delivery
реализован `script/verify-go-web`: два отдельных backend и БД, 12 пар old/new/diff
на трёх viewport, проверка геометрии/шрифтов и точного совпадения пикселей.
Он запускается локально с `LEGACY_ROOT` на зафиксированный checkout; в CI пока
входит только `verify-go-accounts` с Go API и React flow. Подробнее:
[отчёт Go web](go_web_verification.md). Наличие процедуры не означает, что
проверены ещё не перенесённые страницы.

Для первого среза ленты комнаты доступен `WEB_VERIFICATION_SUITE=chat-feed`
в том же скрипте. Он сравнивает карточки на 390×844, 768×1024, 1440×900 и
767×900 и проверяет реальную прокрутку переполненной истории. Это компонентное
сравнение с одинаковой высотой окружающего frame; полный shell/composer ещё
не принят. Условия и снимки: [go_chat_feed_verification.md](go_chat_feed_verification.md).

Для базовых гостевых строк online list доступен `WEB_VERIFICATION_SUITE=chat-online`.
Он сравнивает строки на tablet/desktop без изменения CSS окружения, проверяет
скрытие на 390/767 px, публичное обращение и реальный reconnect/leave.
Область сравнения ограничена гостевыми строками; зарегистрированные настройки,
бот и полная комната ещё не приняты. [Отчёт](go_chat_online_verification.md).

Для полной композиции комнаты добавлен `WEB_VERIFICATION_SUITE=chat-room`:
одинаковые данные в двух disposable БД, одинаковая позиция прокрутки, никаких
CSS overrides или масок. Room/composer/emoji/settings/registration/feedback/profile
снимаются на 390/768/1440 px. [Текущий отчёт](go_chat_room_verification.md).
Для сетевой проверки передачи файла явно включается `RUN_CHAT_P2P=1` в
`script/verify-go-chat`; стандартный прогон сообщает об её отсутствии.

Для раздела помощи доступен `WEB_VERIFICATION_SUITE=help`: оба маршрута
`/help` и `/ranks`, команды и десять званий на 390/768/1440 и границах
640/1024 px. Без масок и допуска, с проверкой метрик/шрифтов и ошибки API.
[Отчёт](go_help_verification.md).

Для приватных настроек аккаунта доступен
`WEB_VERIFICATION_SUITE=account-settings`: форма, focus, три ошибки,
сохранение и reload, 35 full-page пар на 390/639/640/768/1440 px.
Сетевые/CSRF/двухвкладочные сценарии входят в `verify-go-accounts`.
[Отчёт](go_account_settings_verification.md).

Для истории визитов доступен `WEB_VERIFICATION_SUITE=visits`:
пустая/заполненная таблица и мобильная прокрутка на 390/639/640/768/1440 px,
а также авторизованный режим. Реальный вход/выход, снимок до reload,
загрузка и ошибка/повтор входят в `verify-go-chat`.
[Отчёт](go_visits_verification.md).

## Поднять обе версии локально

Для текущего standalone-среза собрать assets в отдельном legacy checkout,
затем из корня репозитория выполнить:

```sh
LEGACY_ROOT=/path/to/pinned/legacy KEEP_MIGRATION_STAND=1 script/verify-go-web
```

Go будет доступен на 4043, Phoenix — на 4044. Скрипт должен оставаться
запущенным; завершение убирает оба сервера и их тестовые БД. Порты можно
задать через `GO_WEB_PORT` и `LEGACY_WEB_PORT`. Ручной Go-стенд на 4040
и auth-тесты на 4042 не затрагиваются.

Ниже сохранена историческая проверка первого React-среза внутри Phoenix;
она не заменяет проверку standalone Go delivery. Из корня репозитория:

```sh
cd apps/phoenix && mix assets.setup
cd apps/phoenix && mix assets.build
cd apps/phoenix && PORT=4030 YOUTUBE_WORKER_URL=http://localhost:4021 YOUTUBE_PROXY_BASE_URL=http://localhost:4021 mix phx.server
```

Открыть в двух вкладках:

- эталон: `http://localhost:4030/profiles`;
- React: `http://localhost:4030/profiles/react`.

Порт 4030 должен быть свободен; уже работающий стенд можно использовать после
проверки его версии. Для анкет worker не требуется; для проверки YouTube он
должен быть отдельно запущен на указанном порту по инструкции в README.

Когда меняются общие CSS, layout, ресурсы или backend, двух маршрутов одной
сборки недостаточно: одна ошибка может одновременно изменить обе страницы.
Тогда поднять старую версию из отдельного worktree на зафиксированном commit,
а новую — из ветки миграции на другом порту. Не переключать checkout с текущими
изменениями. Записать SHA эталона, состояние новой ветки, адреса и команды
запуска обоих стендов в отчёт проверки.

Для чтения текущие маршруты могут использовать одну локальную dev-БД. Для
проверки записи и двух backend-реализаций использовать отдельные тестовые БД
с одинаковыми fixtures; не запускать конкурирующие миграции и записи в общую БД.
При необходимости изолировать также cache, фоновые задачи и внешние интеграции.
Для независимых авторизованных сессий использовать отдельные browser contexts:
разные localhost-порты сами по себе не изолируют cookies.

## Сделать сравнение воспроизводимым

1. Подготовить одинаковые данные: аккаунт/роль, список, сортировку, поисковый
   запрос, номер страницы, выбранную анкету и фотографии. Проверять одну и ту же
   запись, а не два случайных результата. Не брать production-секреты и БД.
2. Использовать один браузер и его версию, одинаковые viewport, device scale,
   zoom 100%, тему и локаль. Сравнивать по очереди при одном размере viewport;
   размещение окон рядом не должно уменьшать одну страницу относительно другой.
3. Дождаться загрузки данных, шрифтов и изображений, стабилизации layout.
   Проверять фактически применённый font, а не только объявление в CSS.
   Loading/error состояния проверять отдельно с управляемой задержкой/ошибкой.
4. Зафиксировать время и данные, исключить случайные значения. Динамические
   счётчики/анимации стабилизировать или маскировать только точечно, с объяснением.
   Не маскировать весь компонент ради успешного сравнения.
5. Снять обе версии в одном состоянии. Сохранить пару изображений old/new
   с одинаковыми размерами и понятным именем сценария; для автоматической
   проверки сохранять также diff. Эталонные снимки не перезаписывать молча.

## Что сравнивать визуально

Минимальные viewport: 390×844 (телефон), 768×1024 (планшет), 1440×900 (desktop).
Дополнительно проверить границы затронутых CSS-breakpoints. Убедиться, что браузер
действительно применил размер; размер панели приложения не равен viewport страницы.

| Область | Проверка |
| --- | --- |
| Типографика | font-family и загруженный шрифт, weight, size, line-height, letter-spacing, переносы и обрезка текста |
| Геометрия | ширина контента, сетка, высота карточек/полей, padding, margin, gap, положение заголовков и кнопок |
| Оформление | цвета, фон, border, radius, тени, затемнение и прозрачность overlay |
| Изображения и иконки | те же ресурсы, размер, пропорции, crop/object-fit, положение и толщина иконок |
| Состояния | default, hover, keyboard focus, disabled, loading, empty, error, открытые диалоги |
| Адаптивность | отсутствие горизонтального overflow и перекрытий, читаемость, прокрутка длинного содержимого и диалогов |

Смотреть снимки рядом и при необходимости накладывать их с прозрачностью.
При расхождении проверять computed styles и размеры элементов. Особенно
проверять семантические теги: замена `h2` на `p` может изменить шрифт через
существующий CSS даже при похожих className.

Незначительный шум сглаживания текста может потребовать небольшой технической
погрешности screenshot-теста. Смена шрифта, переносов, отступов и геометрии не
считается таким шумом. Порог фиксируется и обосновывается; его нельзя увеличивать
только для сокрытия регрессии. Каждое осмысленное визуальное отличие разбирается.

## Проверить одинаковые пользовательские сценарии

Для анкет выполнить в обеих версиях:

- открыть каталог гостем и авторизованным пользователем;
- найти по нику и кириллическому имени, очистить поиск, получить пустой результат;
- быстро менять запрос при медленной сети: старый ответ не заменяет новый;
- перейти между страницами, открыть анкету с фото и без фото, длинным текстом;
- открыть полноразмерное фото, закрыть вложенные диалоги кнопкой и Escape;
- проверить Tab/Shift+Tab, удержание focus в диалоге и его возврат после закрытия;
- проверить URL, прямую ссылку, reload, назад/вперёд и отсутствующую анкету;
- проверить сетевую ошибку и повтор, account controls и выход из аккаунта.

Если старая версия не поддерживает новый URL или другое согласованное поведение,
сравнить эквивалентное состояние через UI и отдельно описать отличие контракта.
Не копировать известную ошибку эталона: исправление оформить явно и проверить.
Для каждого следующего экрана составлять аналогичный список до его переключения.

## Проверить замену Elixir на Go

Запускать один набор контрактных сценариев против обоих локальных backend:
статусы HTTP, JSON-поля и типы, null/отсутствующие поля, порядок и пагинация,
кириллица, ограничения ввода, ошибки, авторизация и CSRF для mutations.
Нормализовать только ожидаемо недетерминированные поля, а не скрывать различия.

Write-сценарии запускать на независимых одинаково подготовленных БД и сравнивать
результирующее состояние, инварианты и события, а не только HTTP 200.
Проверять отказ внешней зависимости, отмену, таймаут, повтор и конкурентные
запросы там, где они влияют на сценарий. После переключения API повторять
браузерные сценарии с тем же React-клиентом. Для realtime дополнительно применять
[правила lifecycle](session_lifecycle.md) и проверки reconnect/presence/порядка событий.

## Автоматизация и принятие этапа

- Запустить текущий `cd apps/phoenix && mix precommit`, сборку и применимые проверки из
  [целевой матрицы](refactoring_target.md). Будущие gates не отмечать пройденными,
  пока они не подключены.
- Добавлять устойчивые browser-сценарии и screenshot-регрессию на критичные
  состояния при внедрении browser test runner. В CI фиксировать среду рендеринга,
  fixtures и viewport; сохранять old/new/diff как артефакты при несовпадении.
- Составить короткий отчёт: версии/URL, данные и роль, размеры экрана,
  проверенные сценарии, результаты команд, пары снимков, найденные различия,
  исправления и оставшиеся ограничения. Не писать «визуально совпадает»,
  если проверялся только один размер или не загружены шрифты.
- Этап готов к ручному принятию, когда сценарии работают, нет необъяснённых
  различий в оформлении, проверки прошли, а старую и новую версии можно открыть
  для сравнения. Передать пользователю оба URL и список того, что проверить.
  Результат ручного принятия записывается в план; CI не заменяет его.

Проверка выполняется локально. Коммит, публикация и production-переключение
остаются отдельными действиями в рамках указаний пользователя.
