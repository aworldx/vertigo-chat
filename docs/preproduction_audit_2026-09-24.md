## Найденные проблемы

### A1 · P1 · Все пользователи за Caddy получают один IP для ограничений

`apps/api/internal/accounts/adapters/http/handler.go:107` берёт только
`r.RemoteAddr`; аналогично entrance, upgrade и WebSocket. В `deploy/Caddyfile`
уже используется `reverse_proxy api:4020`, но доверенного proxy-adapter нет.
`accounts/adapters/postgres/accounts.go` создаёт уникальный суточный guard по
fingerprint этого IP. Следовательно, после первой регистрации через один Caddy
остальные посетители попадают в общий лимит. Гостевые IP-лимиты сообщений тоже
становятся общими. Вывод подтверждён цепочкой конфигурации и кода; отдельный
тест с двумя внешними клиентскими IP через Caddy в этом прогоне не выполнялся.

Нужно единое извлечение client IP с явно доверенными адресами прокси; нельзя
просто доверять любому входящему `X-Forwarded-For`. Закрепить тестами два клиента
за прокси и попытку подделать заголовок при прямом обращении.

### A2 · P1 · N+1 внутри snapshot, суммарно квадратичная нагрузка

`chatsessions/adapters/http/socket.go:139,223` каждую секунду для **каждого**
WebSocket заново получает Presence, историю и представление всех участников.
`cmd/api/chat_preferences.go:96` получает настройки каждого участника, а для
зарегистрированного пользователя повторно читает account на строке 107.
Есть ещё чтение бюджета Хичкока.

При N соединениях и R зарегистрированных участниках получается приблизительно
`N × (N + R + 3)` SQL-запросов в секунду при стандартном включённом бюджете и
незанятом боте, даже без новых сообщений. Для 100 зарегистрированных участников
это 20 300 запросов/с **по структуре алгоритма, не результат бенчмарка**.
Фоновая вкладка не прекращает этот polling.

Нужны пакетное чтение представлений, общий snapshot комнаты/инвалидация по
событиям и тест query budget. Затем измерить latency, pool wait и CPU при
целевом числе одновременных пользователей.

### A3 · P1 · Клиент может скрыть чужое сообщение в ленте

`apps/web/src/features/chat/model/timeline.ts:10` использует только `client_id`
как ключ. БД дедуплицирует по `(room_id, author_identity, client_id)`, то есть
одинаковый client ID разных авторов допустим и передаётся читателям.

Воспроизведено в настоящем браузере: Alice отправляет сообщение, Bob отправляет
свой текст с тем же client ID. В PostgreSQL остаются **2 сообщения**, в ленте
Alice исходное сообщение исчезает, остаётся Bob. Также воспроизведено отдельно
на `publishTimeline`. Нужна идентичность по серверному ID для опубликованных
сообщений и безопасное сопоставление собственного pending-сообщения с ack.

### A4 · P2 · Медиа удерживаются после удаления карточек из UI

`mediaTransfer.ts:78,82,125` хранит `cards`, Blob URL и завершённые audio streams
до `stop()`. `useMediaTransfer.ts:13` оставляет в UI последние 20 карточек,
но не освобождает соответствующие ресурсы менеджера. Таймер 15 минут удаляет
лишь запись `files`; Blob URL продолжает удерживать содержимое файла.

Модельное воспроизведение на исходном коде, с контролируемыми таймерами:
25 файлов → 20 карточек UI → после 15 минут 0 записей `files`, но **25 URL и
25 cards**, ни одного `revokeObjectURL`. Все URL освобождаются только при stop.
Это доказательство удержания ресурсов, не измерение RSS браузера. Для долгой
вкладки с файлами до 50 МБ рост существенен. Нужен явный dispose при eviction,
лимит памяти и защита async-completion после остановки менеджера.

### A5 · P2 · Терминальная сессия продолжает переподключаться

`connection.ts:187` очищает storage при close code 1008, но не останавливает
transport. `socketTransport.ts:71` безусловно планирует следующий connect.
В браузере после 70 секунд offline: сессия закрыта, storage очищен, но число
новых WebSocket-попыток растёт с **1 до 4 за следующие 8 секунд**.

Дополнительно `reconnect():34` не закрывает прежний socket, а обработчики
`onopen/onmessage` не проверяют актуальность экземпляра. Модельный тест:
start → reconnect создаёт 2 открытых socket; stop закрывает только последний;
сообщение старого socket принимается даже после stop. Это отдельный риск гонок,
не утверждение, что обычный offline всегда создаёт две связи.

### A6 · P2 · Offline-очередь молча теряет старые сообщения

`connection.ts:396` ограничивает outbox через `.slice(-50)`, сохраняя старые
pending-элементы в timeline. При 51 отправке без сети первый элемент пропадает
из очереди повторной доставки, хотя остаётся в UI. Это вывод из кода; сценарий
с 51 сообщением в реальном браузере не выполнялся. Следует запрещать новую
отправку при заполнении или явно показывать отказ, а не отбрасывать сообщение.

### A7 · P2 · Загрузка в S3 происходит до проверки квоты треков

`musicchart/application/service.go:43` вызывает `audio.Save` до
`store.Add`:48. Лимит 5 треков проверяется лишь в postgres Store.Add. Поэтому
шестой и последующие файлы могут успешно загрузиться в S3, после чего БД
возвращает ErrLimit; компенсационного удаления нет. Разные файлы оставляют
объекты без ссылок и расходуют storage/трафик. Это статически подтверждённый
порядок операций; реальные лишние объекты в пользовательском S3 не создавались.
Нужна резервируемая квота и cleanup незафиксированных загрузок.

### A8 · P2 · Неограниченные списки и частый polling

Галерея читает все фото (`gallery/adapters/postgres/store.go:28`), библиотека —
все тела статей (`library/adapters/postgres/store.go:32`), хит-парад — все треки
и все комментарии (`musicchart/adapters/postgres/store.go:15,33`).
`useGallery` обновляет весь список каждые 5 секунд, `useChart` — каждые 3 секунды
даже в фоне. Это не N+1 сетевых запросов к PostgreSQL, но работа и размер
ответа растут со всей историей. Нужны pagination/ограничения комментариев,
лёгкие list DTO и приостановка polling в фоне.

### A9 · P2 · Регрессии не блокируют production-сборку в CI

`.gitlab-ci.yml` выполняет Go/unit и frontend static/unit checks, но не поднимает
PostgreSQL для `GO_*_TEST_DATABASE_URL` и не запускает browser-сценарии.
Интеграционные тесты молча skip без этих переменных. Следовательно, зелёный CI
сейчас совместим с ошибками в реальной БД, reconnect и UI. Добавить обязательные
изолированные integration/browser jobs и проверку отсутствия неожиданных skips.

### A10 · P2 · Часть Grafana останется без данных после cutover

Dashboard запрашивает `chat_sessions`, `chat_sessions_reconnecting_total`,
`chat_public_messages_total`, `chat_http_request_duration_milliseconds_bucket`
и `chat_beam_memory_bytes`. Go exporter их не публикует; `chat_http_requests_total`
имеет только `status_class`, без ожидаемого в отдельных панелях `route`.
Новые OpenAI-панели это не исправляют. Нужны метрики Go runtime/pool/WebSocket/
latency и проверка панелей именно на работающем Go exporter, не только promtool.

### Дополнительные риски и архитектура

- В login/entrance нет отдельного throttling неуспешных аутентификаций перед
  PBKDF2. Лимит регистрации и сообщений не защищает подбор пароля и CPU login.
- Учёт OpenAI теряет usage успешного HTTP-ответа с пустым текстом перед retry
  (`bot/adapters/openai/provider.go:112`); ledger также не может восстановить
  расход после успеха провайдера и ошибки записи БД. Это уже ограничение
  мониторинга, описанное в `openai_monitoring.md`; остаток локального бюджета
  нельзя выдавать за точный биллинговый баланс. Costs API без admin key не был
  проверен на живом аккаунте.
- Границы React и domain/application проверяются линтерами, но не гарантируют
  изоляции контекстов: например, musicchart SQL напрямую читает `registered_users`.
  В composition root `chat_preferences.go`, `chat_bot.go`, `karmik.go` живут
  значительные сценарии/транзакции, а не только сборка зависимостей.
- `ChatConnection` (~469 строк) объединяет lock вкладки, transport lifecycle,
  outbox, timeline, настройки, listening и Кармика; `MediaTransfer` (~394 строки)
  объединяет WebRTC, relay, буферизацию, URL и карточки. Разделение ответственности
  стоит делать вместе с regression-тестами A3–A6, не косметической перестановкой.
- Положительные свойства: параметризованные SQL, bounded WebSocket payload,
  cleanup reader/tickers, ограниченные worker queues/cache, отмена группы
  процессов yt-dlp/ffmpeg, CSRF/Origin/cookie boundary, ownership и атомарные
  квоты в PostgreSQL. Массовых `any`/отключений strict в React не обнаружено.

## Продолжение по запросу пользователя

После аудита пользователь поручил довести покрытие до 90% и включить порог
в quality gate отдельно для Go API, React и YouTube worker. Legacy Phoenix
явно исключён из нового требования. Приведённые выше дефекты и проценты описывают
исходный срез; актуальная методика и результаты — в [coverage.md](coverage.md).

- A3: исправлены ключи timeline и сопоставление ack/cancel/private ack; тесты
  сохраняют сообщения разных авторов с одинаковым client ID.
- A4: менеджер теперь вытесняет ресурсы вместе с карточками (20 карточек,
  бюджет 128 МиБ), освобождает URL, streams и ожидания relay при stop. Проверены
  eviction, byte budget, отказ announcement и остановка relay. Это не доказательство
  отсутствия всех утечек: длительный direct P2P/RSS и повторные announcements
  требуют отдельной проверки.
- A5: close 1008 останавливает reconnect; stale socket callbacks игнорируются,
  повторный connect не создаёт параллельный открытый socket. Закреплено тестами.
- A6: заполненная очередь отклоняет новую отправку с видимой ошибкой; тест
  проверяет сохранность первых 50 сообщений.
- A9: новый gate объединяет unit, PostgreSQL и функциональный Chromium coverage,
  отдельно проверяет каждый компонент и блокирует production build ниже 90%.

A1, A2, A7, A8, A10 и исходные visual-различия этим этапом не устранены.
Новый gate не снимает запрет на production cutover до устранения блокеров.
