# Architecture Conventions

Этот документ фиксирует архитектурные договоренности проекта. Его цель - держать код простым, понятным и расширяемым, пока чат растет от realtime-прототипа до полноценного продукта с регистрацией, анкетами, личкой, фотоальбомом, модерацией и админкой.

## Главная идея

Проект строится вокруг Phoenix Contexts и принципов чистой архитектуры:

- `ChatWeb` отвечает только за web-слой: роуты, LiveView, контроллеры, компоненты, формы, отображение ошибок.
- `Chat` и вложенные контексты отвечают за бизнес-логику.
- `Chat.Repo`, Ecto-схемы и миграции отвечают за хранение данных.
- Инфраструктура вроде PubSub, Presence, файлового хранилища, email и внешних API должна быть спрятана за небольшими публичными функциями контекстов.

Web-слой не должен становиться местом, где живут правила продукта.

## Слои

### Presentation layer

Папка: `lib/chat_web`

Сюда относятся:

- LiveView-модули;
- контроллеры;
- компоненты;
- роутер;
- шаблоны `.heex`;
- web-only helpers.

Задачи слоя:

- принять ввод пользователя;
- вызвать публичную функцию контекста;
- отрисовать результат;
- обработать UI-состояния вроде loading, flash, selected tab.

Нельзя:

- писать SQL/Ecto-запросы прямо в LiveView или контроллере;
- хранить бизнес-правила в шаблонах;
- напрямую управлять файловым хранилищем, email, банами, ролями и правами из UI-модуля;
- смешивать сложную бизнес-логику с `handle_event/3`.

### Application/domain layer

Папка: `lib/chat/*`

Каждая крупная область продукта оформляется отдельным контекстом:

- `Chat.Accounts` - пользователи, регистрация, сессии, роли;
- `Chat.Profiles` - анкеты, фото профиля, информация о себе;
- `Chat.Rooms` или `Chat.Messages` - комнаты, публичные сообщения, история;
- `Chat.Chatlans` - онлайн-чатлане, Presence, гостевые ники и публичный вид в чате;
- `Chat.PrivateMessages` - личные сообщения;
- `Chat.Library` - публичные авторские статьи и серии;
- `Chat.Gallery` - общий фотоальбом;
- `Chat.Visits` - кто был и когда;
- `Chat.Moderation` - жалобы, муты, баны, удаление сообщений;
- `Chat.Admin` - административные сценарии, если они не укладываются в обычные контексты.

Задачи слоя:

- принимать простые данные от web-слоя;
- проверять правила продукта;
- работать с Ecto-схемами и Repo;
- возвращать понятный результат: `{:ok, value}` или `{:error, reason_or_changeset}`.

Контекст должен иметь маленький публичный API. Например:

```elixir
Chat.Messages.send_public_message(user, room, attrs)
Chat.Messages.list_recent_messages(room)
Chat.Moderation.ban_user(admin, user, attrs)
Chat.Visits.mark_online(user)
```

### Data layer

Папки:

- `lib/chat/**` для Ecto-схем;
- `priv/repo/migrations` для миграций;
- `priv/repo/seeds.exs` для стартовых данных.

Правила:

- Ecto-схемы описывают структуру данных и changesets.
- Запросы должны жить в контекстах или небольших query-модулях внутри контекста.
- Миграции должны быть маленькими и обратимыми, когда это реально.
- Связи, которые используются в шаблонах, нужно preload-ить заранее в контексте.

### Infrastructure layer

Сюда относятся:

- `Phoenix.PubSub`;
- `Phoenix.Presence`;
- загрузка файлов;
- email;
- внешние API;
- фоновые jobs;
- Redis/S3, если появятся позже.

Правило: инфраструктура не должна протекать по всему приложению. Например, LiveView может использовать PubSub для realtime-подписки, но сохранение сообщения, проверка прав, модерация и рассылка событий должны постепенно переехать в контекст `Chat.Messages`.

Адаптер Presence расположен в `Chat.Presence`, чтобы доменные контексты не зависели от `ChatWeb`.

## Зависимости между слоями

Разрешенное направление зависимостей:

```text
ChatWeb -> Chat contexts -> Repo / external adapters
```

Запрещенные направления:

```text
Chat -> ChatWeb
Repo/schema -> ChatWeb
Template -> Repo
Controller/LiveView -> random infrastructure without context
```

Бизнес-слой не должен знать о LiveView, sockets, assigns, flashes, HTML или CSS.

## LiveView conventions

LiveView можно использовать активно, потому что чат realtime. Но LiveView должен оставаться тонким.

В LiveView допустимо:

- хранить UI-состояние;
- подписываться на PubSub/PRESENCE topics;
- вызывать контексты;
- обновлять streams;
- валидировать форму на уровне UX.

В LiveView нежелательно:

- собирать сложные Ecto-запросы;
- решать, имеет ли пользователь право модерировать;
- реализовывать алгоритмы антиспама;
- напрямую писать в несколько таблиц;
- превращать `handle_event/3` в сценарий на 100 строк.

Если `handle_event/3` стал сложнее 10-20 строк, почти всегда нужна функция в контексте.

## Naming

Имена модулей должны отражать слой:

- `ChatWeb.RoomLive` - web/UI;
- `Chat.Messages` - публичный API контекста;
- `Chat.Messages.Message` - Ecto-схема;
- `Chat.Messages.Query` - query helpers, если запросов много;
- `Chat.Moderation.Ban` - Ecto-схема или доменная структура внутри контекста.

Имена функций должны говорить о действии пользователя или бизнес-событии:

- хорошо: `send_public_message/3`, `delete_message/2`, `mark_visit/1`;
- хуже: `create/1`, `do_update/2`, `process/1`, если из имени непонятен смысл.

## Result conventions

Публичные функции контекстов обычно возвращают:

```elixir
{:ok, value}
{:error, %Ecto.Changeset{}}
{:error, :forbidden}
{:error, :not_found}
{:error, :rate_limited}
```

Исключения оставляем для действительно неожиданных ошибок, а не для обычных пользовательских сценариев.

## Authorization and moderation

Права не должны проверяться только в UI.

Правильно:

- UI скрывает кнопку модерации для обычного пользователя;
- контекст `Chat.Moderation` все равно проверяет роль перед действием.

Нельзя полагаться на то, что пользователь "не увидит кнопку".

## Realtime conventions

Realtime-события должны быть предсказуемыми.

Рекомендуемые topic names:

```text
room:<room_id>
user:<user_id>
moderation
presence:room:<room_id>
```

Рекомендуемые события:

```elixir
{:message_created, message}
{:message_deleted, message_id}
{:user_muted, user_id}
{:profile_updated, profile}
```

Сначала изменение состояния проходит через контекст и БД, потом публикуется realtime-событие. Исключение - временные UI-события вроде typing indicator.

## Testing

Тесты должны соответствовать слоям:

- контексты тестируются через `DataCase`;
- web/LiveView - через `ConnCase` и LiveView test helpers;
- сложные права и модерация тестируются на уровне контекста;
- realtime-события тестируются через PubSub subscribe/assert_receive.

Для новой бизнес-фичи минимум один тест должен проверять контекст, а не только UI.

## Когда можно нарушить правило

Можно временно нарушить правило ради быстрого прототипа, если:

- это явно помечено коротким комментарием или задачей;
- понятно, куда код переедет;
- нарушение не становится шаблоном для новых фич.

Текущий `RoomLive` все еще прототипный в части гостевых пользователей, онлайн-списка и временной истории сообщений. Регистрация, проверка пароля и правила входа вынесены в `Chat.Accounts`, отправка сообщений - в `Chat.Messages`, внешний вид чатланина - в `Chat.Appearance`. При добавлении постоянного хранения сообщений следующий шаг - добавить Ecto-схему `Chat.Messages.Message`, миграцию и сохранение сообщения перед публикацией realtime-события.
