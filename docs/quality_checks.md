# Проверки Go + React

## Целевые проверки перед выпуском

По решению пользователя от 2026-10-04 перед push, merge и production-обновлением
достаточно целевых проверок изменений с учётом возможных побочных эффектов.

- Определите весь состав выпуска и затронутые зависимости: общие компоненты и стили,
  API/DTO, состояние и события, права доступа, БД, конфигурацию и потребителей изменений.
- Запустите в Docker соответствующие unit/HTTP/PostgreSQL-тесты, статические проверки
  изменённой поверхности и регрессионные сценарии её зависимостей. Для UI основной
  агент обязательно использует `verifier` и целевые browser-сценарии.
- При изменении контрактов проверьте генерацию DTO и потребителей; при изменении
  схемы БД — миграции и затронутые операции; при изменении общих стилей или компонентов —
  использующие их экраны и размеры; при изменении инфраструктуры — её конфигурацию.
- Зафиксируйте, что проверено и почему этого достаточно, результаты и непроверенные
  риски. Обнаруженные регрессии исправьте и расширьте соответствующие целевые проверки.

Полный `script/check` не является обязательным release gate; запускайте его только
по отдельному запросу пользователя. Тесты и пороги покрытия не удаляются и не ослабляются.

## Полный набор проверок

Запуск по запросу: `script/check`. На компьютере требуется только работающий Docker.
Локальные Go, Node, PostgreSQL, Elixir и временные SDK не используются.

Первая сборка загружает Go 1.27.1, Node 24.8.0, Chromium из Playwright lockfile,
ImageMagick, PostgreSQL client и закреплённые линтеры. Последующие запуски
используют слои Docker и отдельный Go build cache. Изменение исходников не
переустанавливает браузер и npm-пакеты; изменение lockfile обновляет зависимости.

Каждый запуск получает свою Docker-сеть, PostgreSQL 17 и runner. Порты не
публикуются, production/dev базы не используются. Секреты и Docker socket не
передаются контейнеру; исходники копируются через `.dockerignore`. Runner и БД
с их томом удаляются при завершении, в том числе при ошибке.

Проверяются DTO, TypeScript, ESLint/границы архитектуры, Prettier, gofmt, vet,
Go race tests, golangci-lint/depguard, unit + PostgreSQL + browser coverage,
сборки frontend, аккаунты, чат/плеер/поиск, Тетрис, разделы сайта, ShellCheck,
Hadolint, OpenAPI и Compose config. Пороги покрытия не снижены.
Лог, итоговые JSON-отчёты покрытия и снимки копируются в `coverage/quality/`
даже при неуспехе тестов. Сырые браузерные данные покрытия не копируются:
они занимают несколько гигабайт и нужны только для агрегации внутри runner.

`script/check-target` — внутренние Linux-шаги образа. Вызов отдельных проверок
на хосте требует самостоятельно установленного окружения; целевые проверки выполняйте
в Docker с закреплёнными инструментами. Phoenix/LiveView comparisons сохранены только как явно запускаемые
legacy-проверки (`npm --prefix apps/web run test:browser:legacy`).

## Хранение визуальных артефактов

Макеты, исходные иллюстрации и browser PNG хранятся локально в `docs/design/`
вне Git; каталог целиком исключён из Docker build context. Отчёты, capture/compare
скрипты и контрольные суммы могут быть в Git. Перед переносом проверки на другую
машину отдельно перенесите нужный комплект эталонов; отсутствие PNG не означает
успешное визуальное сравнение. Не добавляйте изображения принудительно через git add -f.
Изображения, которые приложение действительно загружает, остаются в
`apps/web/public/` и включаются в production-сборку.
