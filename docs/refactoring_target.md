# Целевая архитектура и правила рефакторинга

Статус: принято как направление миграции. Это требования к целевому состоянию,
а не утверждение, что текущий код и CI уже им соответствуют. Фактическое состояние
и последовательность внедрения перечислены ниже. Изменение структуры, проверок
и поведения выполняется отдельными проверяемыми шагами.

Статус работы, ограничения и инструкция для следующих сессий находятся в
[плане переезда на Go + React](go_react_migration_plan.md).

## Монорепозиторий

Один Git-репозиторий, отдельные приложения и сборки. Общий репозиторий позволяет
согласованно менять контракт, сервер и клиент, но не требует общего релиза.

```text
chat/
├── apps/
│   ├── web/                         # React + TypeScript
│   │   ├── src/
│   │   │   ├── app/                 # запуск, маршруты, провайдеры, композиция
│   │   │   ├── pages/               # сборка экранов из возможностей
│   │   │   ├── features/            # возможности продукта: profiles, gallery…
│   │   │   │   └── profiles/
│   │   │   │       ├── ui/          # компоненты отображения
│   │   │   │       ├── model/       # состояние, hooks, чистые преобразования
│   │   │   │       ├── api/         # запросы и преобразование DTO
│   │   │   │       └── index.ts     # публичный API возможности
│   │   │   └── shared/              # UI-примитивы, HTTP, сгенерированные типы
│   │   └── package.json
│   ├── api/                         # модульный основной бэкенд на Go
│   │   ├── cmd/api/                 # composition root: создание зависимостей
│   │   ├── internal/
│   │   │   └── profiles/            # пример bounded context
│   │   │       ├── domain/          # правила и предметные типы
│   │   │       ├── application/     # сценарии и необходимые им порты
│   │   │       └── adapters/        # HTTP, PostgreSQL, внешние сервисы
│   │   ├── migrations/             # миграции данных, принадлежащих Go API
│   │   └── go.mod
│   └── phoenix/                     # существующее приложение до его замены
│       ├── lib/
│       ├── priv/repo/migrations/
│       └── mix.exs
├── services/
│   └── youtube-worker/              # отдельный Go-модуль и образ
│       ├── cmd/youtube-worker/
│       ├── internal/                # сценарии подготовки/поиска и адаптеры
│       └── go.mod
├── contracts/                       # OpenAPI и схемы realtime-событий
├── deploy/                          # Docker, Compose, окружения и мониторинг
├── script/                          # общие команды проверки и разработки
└── docs/                            # архитектура, решения и эксплуатация
```

Дерево задаёт ответственность каталогов; пустые каталоги заранее не создаём.
Каждый Go-сервис имеет собственный `go.mod`; зависимости фронта фиксируются
lock-файлом. Общие runtime-пакеты выделяем только при реальном повторном
использовании. Общая папка с бизнес-моделями всех сервисов не нужна.

React asset pipeline расположен в `apps/web`, Phoenix — в `apps/phoenix`,
воркер — в `services/youtube-worker`, контракты — в `contracts/openapi`, а
Docker/Compose/monitoring — в `deploy`. Смена каталогов сама по себе не должна
менять маршруты, внешний вид, данные или порядок деплоя.

## Clean Architecture и DDD

- Начинаем с предметных областей и сценариев пользователя. `Accounts`, `Profiles`,
  сообщения и модерация имеют явные границы и небольшой публичный API.
  Bounded context не означает обязательный отдельный микросервис.
- Домен содержит инварианты, value objects и сущности, где они нужны предметной
  модели. Он не зависит от HTTP, SQL, React, файловой системы или subprocess.
  Простому поиску не нужны искусственные агрегаты и фабрики.
- Application-слой организует сценарии, авторизацию и границы транзакций.
  Домен повторно защищает свои инварианты независимо от входного адаптера.
- Внешние адаптеры реализуют порты application-слоя. Интерфейс в Go объявляется
  у потребителя и остаётся минимальным. Зависимости связывает composition root;
  глобальные service locator и изменяемые singleton-зависимости запрещены.
- Направление импортов в Go: `adapters → application → domain`.
  `application` не импортирует адаптеры; `domain` не импортирует внешние слои.
  Стандартная библиотека допустима, если не привносит инфраструктурную зависимость.
- Между контекстами используются публичные application API или явные события.
  Запрещены импорты внутренних моделей/репозиториев другого контекста и доступ
  к его таблицам в обход владельца. Между сервисами — документированные контракты.
- У каждой области данных один владелец записи и миграций. При переходе
  Elixir → Go владение передаётся явно; параллельная запись двумя реализациями
  и дублирование бизнес-правил не допускаются.
- HTTP DTO, модели хранения и доменные типы разделяются на границах.
  Сериализация сущностей БД напрямую в публичный API запрещена.
- Ошибки предметной области не содержат HTTP-кодов. Адаптер переводит их
  в согласованный ответ API. Таймауты, отмена, повторы и идемпотентность
  задаются явно там, где есть внешние операции.

Существующий Phoenix использует практические границы контекстов из
[architecture.md](architecture.md): контексты пока работают с Ecto/Repo.
Это переходное устройство, а не образец строгой изоляции домена для нового Go-кода.
Выделять repository-интерфейс для каждой CRUD-функции без потребности не нужно.

## React и TypeScript

- Весь новый React-код и его тесты пишутся на TypeScript (`.ts`/`.tsx`).
  Целевой набор: `strict`, `noUncheckedIndexedAccess`,
  `exactOptionalPropertyTypes`, `noEmit`. Сборка esbuild не заменяет `tsc`.
  Старые LiveView hooks на JavaScript переносятся отдельно.
- Запрещены необоснованные `any`, non-null assertions и приведения типов,
  скрывающие ошибку. Внешние данные сначала имеют тип `unknown` и проверяются
  на границе; типы TypeScript не являются runtime-валидацией JSON.
- Типы API выводятся из контракта, не поддерживаются вручную в двух местах.
  Сгенерированные DTO преобразуются в модели UI в `api/`.
- Направление импортов: `app → pages → features → shared`; нижние слои
  не импортируют верхние. Возможности не импортируют друг друга напрямую:
  их взаимодействие организуется страницей или application-композицией.
  Импорты извне возможности идут через её публичный API. Циклы запрещены.
- Компонент отображает props и UI-состояние, обрабатывает пользовательские
  события. Render чистый: без сетевых запросов, записи в storage и мутаций
  props/state. Побочные эффекты находятся в обработчиках или специализированных hooks.
- Страница соединяет компоненты; запросы находятся в `api/`, управление
  запросами/URL/состоянием — в `model/`. Один большой hook вместо одного
  большого компонента тоже нарушает разделение ответственности.
- Не храним вычисляемые значения в отдельном state, не используем effects
  для обычного вычисления данных. Соблюдаем Rules of Hooks и зависимости effects;
  запросы учитывают отмену, ошибки и устаревшие ответы.
- Компоненты выделяются по ответственности: поиск, список, карточка,
  пагинация, диалог профиля и просмотр фото. `shared` содержит действительно
  общие примитивы; каталоги `utils`/`helpers` не становятся складом логики.
- DOM остаётся семантическим: подписи, клавиатура, focus management,
  loading/empty/error состояния. Миграция сохраняет существующие шрифты,
  дизайн и поведение, если изменение продукта не согласовано отдельно.
- Размер и сложность функций ограничиваются статическими правилами с
  документированными порогами. Формальное деление по числу строк не заменяет
  разделения ответственности. `memo`, глобальный store и абстракции добавляются
  по необходимости, а не во все компоненты автоматически.

Базовые источники правил: [React Rules](https://react.dev/reference/rules),
[TypeScript strict](https://www.typescriptlang.org/tsconfig/strict.html),
[typescript-eslint typed linting](https://typescript-eslint.io/getting-started/typed-linting/).

## Обязательные автоматические проверки

Каждое приложение и сервис обязаны иметь formatter, linter/static analysis
и релевантные тесты. Версии инструментов фиксируются; конфигурации хранятся
в репозитории. Локальная общая команда и CI вызывают одинаковые проверки.
В CI форматирование только проверяется, файлы не исправляются автоматически.

| Область | Целевые проверки |
| --- | --- |
| React / TypeScript | `tsc --noEmit`; ESLint flat config с typescript-eslint `strictTypeChecked`, React Hooks и JSX accessibility; Prettier check; тесты пользовательских сценариев; production build |
| Границы фронта | ESLint boundaries/import restrictions и проверка циклов: направления слоёв, публичные entry points, запрет обхода границ через alias или относительный путь |
| Каждый Go-модуль | `gofmt`; `go vet`; golangci-lint с явным набором `staticcheck`, `errcheck`, `ineffassign`, `unused`, `govet`, `depguard`, `gocyclo`; `go test -race ./...`; сборка |
| Границы Go | `internal` visibility и правила `depguard` для domain/application/adapters и контекстов; архитектурные тесты графа импортов для ограничений, которые не выражаются конфигурацией |
| Phoenix / Elixir | `mix format --check-formatted`; компиляция с `--warnings-as-errors`; Credo strict; Dialyzer; ExUnit; проверка запрета зависимости `Chat → ChatWeb` и обхода контекстов |
| Контракты | OpenAPI lint, проверка совместимости с базовой веткой, актуальность сгенерированных типов, контрактные тесты клиента и сервера |
| Инфраструктура | ShellCheck для shell-скриптов, Hadolint для Dockerfile, проверка конфигурации Compose на тестовых значениях без production-секретов |

Состав Go-линтеров сверяется с
[официальным каталогом golangci-lint](https://golangci-lint.run/docs/linters/)
при фиксации версии. Не включаем все доступные правила без разбора; для каждого
должна быть понятна проверяемая ошибка или договорённость.

Статический анализ должен проверять всё, что можно выразить надёжным правилом:
типы, импорты, циклы, необработанные ошибки/Promise, правила hooks, доступность
разметки, форматирование и сложность. Сами инварианты продукта и правильность
выделения bounded contexts проверяются тестами и ревью. Линтер не доказывает DDD.

Новая ошибка блокирует принятие изменения. Отключение правила допускается
только точечно с причиной и задачей удаления исключения. Общий `eslint-disable`,
отключение strict или исключение целого сервиса ради зелёной проверки запрещены.
Для legacy-долга допустим явный ограниченный baseline с задачами исправления;
новые нарушения в него автоматически не добавляются.

## Что уже работает и что предстоит

На момент принятия этого документа:

| Область | Фактическое состояние |
| --- | --- |
| React | Строгие TypeScript, ESLint (включая cycles и границы entry point), Prettier, interaction- и browser/screenshot-тесты входят в `mix precommit` |
| Go worker | `script/check-go` выполняет `gofmt`, `go vet`, golangci-lint 2.13.2 (`staticcheck`, `errcheck`, `ineffassign`, `unused`, `govet`, `depguard`, `gocyclo`), race-тесты и сборку; `depguard` заранее закрепляет направление для будущих Go слоёв |
| Elixir | `cd apps/phoenix && mix precommit`: компиляция с warnings-as-errors, форматирование, Go/React/ExUnit-тесты, Dialyzer и строгий Credo через `script/check-credo`; 100 legacy-замечаний зафиксированы в проверяемом baseline, новые нарушения блокируют проверку |
| CI | Quality target с закреплёнными инструментами запускается для merge requests и default branch перед production image build; тесты используют изолированную PostgreSQL |
| Контракты / инфраструктура | Генерация DTO проверяется без зависимости от Git, Redocly 1.34.5 lint проверяет OpenAPI; ShellCheck 0.10.0, Hadolint 2.12.0 и `docker compose config` с test-значениями входят в `script/check` |

Порядок работ:

1. До переноса следующего экрана перевести текущие React-анкеты и тесты на
   строгий TypeScript, разделить UI/model/api и включить проверки фронта.
   Проверить прежние поиск, пагинацию, диалоги, URL и внешний вид в браузере.
2. Подключить проверки оставшихся сервисов, контрактов и границ; разобрать
   найденный долг. Сделать общий `script/check` и CI quality для merge requests
   и default branch обязательными перед сборкой релизных образов.
   До появления этой команды текущая точка входа — `cd apps/phoenix && mix precommit`.
3. Переносить каталоги отдельными изменениями с рабочими локальным стендом,
   сборками и проверками. Сначала web/worker, затем Phoenix по необходимости.
4. Переносить следующие UI-сценарии и только затем отдельные backend-контексты
   на Go за совместимым API. Новый сервис сразу получает полный набор проверок.

Изменение считается завершённым, когда соблюдены границы ответственности,
пройдены применимые автоматические проверки и тесты поведения, обновлён контракт
при его изменении и вручную проверен затронутый UI. Для перехода области данных
также описываются владелец записи, миграции и откат. Публикация и деплой являются
отдельными действиями; фиксация этого плана их не запускает.

Для UI обязательно [сравнение обеих локальных версий](migration_testing.md)
на одинаковых данных и viewport: поведение, шрифты, стили и снимки ключевых
состояний. Необъяснённые визуальные отличия исправляются до принятия этапа.
